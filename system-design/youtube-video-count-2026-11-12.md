# Visible YouTube result count

November 12, 2026. **Videos to fetch** now appears beside Sources and Date range in the Search control panel. It accepts every whole number from 1 to 20 and defaults to 10. This is the current bounded provider/context pool limit, not a claim about YouTube’s maximum API page size. Results can be fewer because of provider availability, filters or relevance review.

The choice is remembered in this browser with source/date preferences and shared with Exploration chat. Existing preferences without a count migrate to 10; invalid stored values fall back to 10 without discarding valid source/date choices. Removing YouTube disables its Search control but retains the chosen number. Edits make no search/provider call and apply when the user starts the next query. Opening an old search does not replace the next-search preference. New saved searches report their original requested video count separately from their actual returned resources.

The value is an explicit `video_count` in conversation creation, discover turns and direct research requests. Conversations inherit the last recorded count when a turn omits it; an explicit override becomes the next default for that conversation. Each provider child, including AI retrieval repairs, receives the approved count. It affects only YouTube: its per-branch and union limits and upstream `maxResults` use the selected value. Paper providers retain their existing limits. Server validation rejects out-of-range, fractional, boolean and string counts before dispatch.

The original 20-record context/retention envelope remains intact. This control requests a maximum per YouTube provider query; AI retrieval can perform another bounded query when its existing repair policy allows it. The count is not a promise of that many relevant videos. Default direct-run and omitted-turn idempotency identities remain compatible with historical requests, while an explicit count change is bound to a different request identity.

The YouTube lexical cache now has a count-aware policy marker. Earlier code keyed a nominal 20-record pool while requesting only ten upstream videos; those persisted entries must not silently limit a new request for twenty. Count-specific cache keys and immutable original-operation replay remain separate: saved results are preserved, and new requests use the correct count-aware pool.

`GET /api/config` exposes `{ default: 10, min: 1, max: 20 }` plus the current request allowances. The provider’s eight-request run allowance is shown separately in the UI, with metadata/caption work explained. This change does not raise provider, overall or model budgets. Selecting twenty videos requests a larger result page and does not grant twenty metadata or caption lookups.
