# Project Research Resource Guide

Research papers, datasets, code and the other sources needed to take a project from idea to implementation

Compiled October 25 2026. Sources reviewed October 24 and 25 2026.

## What to use first

For most projects, start with a small combination of complementary sources: one broad paper index, one specialist source, an original dataset repository, a code host, official technical documentation, an evaluation source and a reference manager. Expand only when the question or coverage gap calls for it. No single website reliably provides all the evidence, implementation assets and permissions a project needs.

This report contains **142 directory entries across 14 categories**, with destination links, programmatic access documentation, MCP status and practical access or reuse considerations. Several entries group related services, and Hugging Face datasets and models are covered separately because they solve different tasks. The count describes directory entries, not 142 distinct organizations.

The strongest general starting combination is **Google Scholar for manual discovery; OpenAlex and Semantic Scholar for programmatic literature search; Kaggle, Hugging Face and a domain repository for data; GitHub for implementation; official documentation for integration; and Zotero for provenance**. Add the original government, scientific or institutional source whenever accuracy and updates matter.

The most useful sources beyond papers, datasets and code are benchmarks, standards, package and vulnerability registries, user discussions, patents, company filings, funding records, design assets and identity registries. They answer different questions: whether a method works, whether it can be implemented safely, whether people need it and whether the inputs can actually be reused.

## How to choose between sources

### Separate discovery from the source of record

Search engines and aggregators are useful for finding candidates. Original repositories, publishers and data-producing agencies are usually better places to resolve versions, definitions and permissions. Google Dataset Search can reveal a dataset, DataCite can identify its DOI and Zenodo can host a particular release; those are complementary functions rather than interchangeable products.

Likewise, a paper index is not necessarily a full text library, and a metadata API is not necessarily a file-download API. A repository may expose searchable metadata while keeping individual files restricted. Check access at the level of the particular artifact you need.

### Use multiple evidence types

A paper provides a claim and method. A dataset provides observations. Code reveals implementation choices. A benchmark measures performance under a particular setup. Standards define expected behavior. User research establishes needs and constraints. Strong project decisions connect these evidence types instead of treating citations, downloads or repository stars as sufficient validation.

For a consequential claim, look for the original study or official record, an independent replication or review and evidence that the result transfers to your intended setting. Community posts and AI-generated summaries are useful leads; use the underlying sources to support the final claim.

### Apply a practical selection rubric

The following weights are a recommended decision aid, not measured ratings of the services in this report. Score each candidate from 0 to 5 and calculate the weighted average. Treat unavailable permissions or unusable data as a reason to reject the candidate regardless of its score.

| Criterion | Weight | What to inspect |
|---|---|---|
| Fit to the problem | 30 percent | Population, modality, geography, target, labels, deployment setting and actual question. |
| Provenance and evidence | 25 percent | Original producer, methods, documentation, citations, collection process and reproducibility. |
| Coverage and freshness | 20 percent | Update cadence, missingness, historical depth, revisions and known sampling gaps. |
| Operational usability | 15 percent | Stable identifiers, versioning, supported API or downloads, quotas and realistic cost. |
| Completeness of supporting material | 10 percent | Data dictionary, code, baseline, quality flags, examples and contact or maintenance information. |

## A repeatable project research workflow

1. **Define the decision.** Write the problem, intended users, constraints and success metric before searching. Identify whether the project needs evidence, data, an implementation, an integration or all four.
2. **Map the vocabulary.** Read a review or authoritative overview and collect synonyms, domain terms, relevant venues and dataset names. Search both the method and the application problem.
3. **Build an evidence map.** Select a few strong seed papers. Read their references and newer citing work. Include contradictory findings, negative results and limitations rather than only successful examples.
4. **Find the actual artifacts.** Follow DOI, repository, supplementary material and dataset links. Identify which code and data versions generated the reported result. Resolve missing artifacts before relying on reproducibility claims.
5. **Audit the data.** Inspect schema, label meaning, sample size, collection period, missingness and subgroup coverage. Check duplicate observations and whether the train and test sets overlap by person, organization, geography or time.
6. **Reproduce a modest baseline.** Run an official or well-supported implementation on a small sample. Record versions, environment and costs. Establish that access and data quality are adequate before scaling.
7. **Evaluate for the real use case.** Keep a project-specific holdout set, test relevant failure cases and measure the outcome that matters to users. Published leaderboard results are inputs to this decision, not substitutes for it.
8. **Record the evidence chain.** Save source IDs, retrieval dates, licenses, versions, transformations and reasons for selecting or rejecting resources. Recheck volatile integrations and datasets before release.

Useful query patterns include a topic plus "systematic review" or "survey"; a paper title plus "code" or "dataset"; a target variable plus "data dictionary"; and a library name plus its exact version and "official documentation". Search a specialist index when broad results miss the field's terminology.

## APIs MCP and what the status labels mean

An **API** is a documented interface that software can call. An **SDK** is a programming library, which may wrap an API or work locally. **Bulk files** can be the best interface for large, reproducible analysis. **MCP** exposes selected capabilities as tools to an AI client. MCP does not expand your account permissions, remove provider quotas or change the underlying content license.

Use the official API or bulk downloads for scheduled ingestion, large exports and workflows that need precise requests, retries and versioned outputs. Use MCP for interactive discovery, navigation and tool-assisted exploration when the server exposes the required operations. A thin custom integration over an official API is often more dependable than an unmaintained community connector.

### API labels used in the directory

**HTTP API** means a documented HTTP interface exists, although authentication or payment may apply. **Restricted API** means approval, institutional entitlement, a commercial agreement or comparable access conditions are material. **SDK or local interface** means the verified route is an official client or local programmatic tool; it is not a claim of an unrestricted public REST API. **Bulk files or Git** means machine access through downloads or repositories. **Web only verified** means manual access was verified and a generally available public API was not established.

### MCP labels used in the directory

**Official** means the provider documents or maintains the server. **Community** means an independent connector implementation was located in its maintainer's repository. **Project supported** means the upstream project documents or endorses an integration that should not be confused with a mature provider service. **Not verified** means no qualifying server was established in this review; it does not mean that none exists.

Community connectors are examples of available implementations, not endorsements or successful installation tests. The directory links to original documentation or repositories so ownership can be inspected. A server's presence in the Official MCP Registry does not make it an official integration of the data provider.

### Useful confirmed official MCP options

The report identifies provider-documented MCP integrations for [OpenAlex](https://help.openalex.org/access/connector/), [Kaggle](https://www.kaggle.com/docs/mcp), [Hugging Face](https://huggingface.co/docs/hub/en/agents-mcp), [GitHub](https://github.com/github/github-mcp-server), [GitLab](https://docs.gitlab.com/user/model_context_protocol/mcp_server/), [FRED](https://fred.stlouisfed.org/help/data/connecting-fred-to-ai-services/fred-mcp-connector), [World Bank Data360](https://worldbank.github.io/data360-mcp/), [MDN](https://developer.mozilla.org/en-US/mcp), [Figma](https://developers.figma.com/docs/figma-mcp-server/) and several retrieval services. RCSB's official server is beta. World Bank Data360, BigQuery, Snowflake and Postman connectors have specific service or account scopes; do not assume they cover every product or dataset associated with the provider.

Before choosing a connector, inspect the publisher, supported tools, authentication method, maintenance history and data destination. Verify that it can search or fetch the exact artifact you need. Start with the narrowest required permissions and test a representative read operation.

## Important findings and common traps

**Google Scholar is excellent for manual discovery but a poor foundation for bulk automation.** Its help page says bulk access is unavailable and directs automated users to respect its access rules. A third-party Scholar scraper is not an official Google API. Use a supported index API when repeatability matters. [Source](https://scholar.google.com/intl/en/scholar/help.html).

**A dataset being downloadable does not establish that it is appropriate or reusable.** Trace mirrored datasets to the original producer. Check the artifact's license, collection method, version and population. Data portals frequently contain a mixture of public, gated, restricted and third-party materials.

**Open access, open data, open source and open weights describe different permissions.** Inspect the license of the paper, data, code and model separately. API subscription terms, attribution obligations, restrictions on redistribution and training rights may also differ. Preserve the relevant terms alongside the artifact version.

**Current integration instructions matter.** The current [Data.gov catalog documentation](https://resources.data.gov/catalog-api/) describes a replacement for the previous CKAN API. [Mendeley Data's current API documentation](https://data.mendeley.com/api/docs/) identifies superseded hosts and authentication. Use current provider guidance rather than old tutorials.

**Papers with Code should be treated as a legacy discovery reference.** Its website redirected to Hugging Face Trending Papers when checked. Use [Hugging Face Papers](https://huggingface.co/papers/trending), original paper repositories and current benchmark projects. The redirect does not establish that every historical leaderboard or API has been preserved. [Original project issue](https://github.com/paperswithcode/paperswithcode-data/issues/116).

**Benchmark access is not validation.** Random row splits can leak people, places or future information across train and test sets. For historical forecasting or financial backtests, use data available at the decision time. For model or agent comparisons, preserve the benchmark revision, prompt or harness, tools and compute conditions.

**Community sources are useful for discovery, debugging and hypotheses.** They are weaker support for scientific claims, representative demand estimates or definitive product behavior. Verify important statements against primary evidence and collect direct user feedback for your own audience.

**Access restrictions can determine the architecture.** PhysioNet explicitly cautions against sharing credentialed data with third parties, including external API services. Some projects therefore require approved local processing rather than sending their data to a hosted assistant. [PhysioNet guidance](https://physionet.org/).

## How this report was compiled

Sources were selected to cover the main stages of a research-informed software or data project: discovery, evidence, inputs, implementation, evaluation, user needs and provenance. Primary provider documentation and original maintainer repositories were preferred for integration claims. Search results were used to locate those sources, and specific access limitations were retained when they materially affect use.

API and MCP status describes documented availability, not a successful authenticated call, installation, performance benchmark or security audit. Commercial subscriptions, quotas and access rules can change. Exact prices and request limits are intentionally not frozen into this directory; the linked provider documentation is the operational reference.

Some pages were blocked, required JavaScript or could not be fully fetched. In particular, direct access to Libraries.io's API page, some ACM and SSRN pages and the India API directory was limited. These entries retain available primary references and conservative status wording. They require a fresh access check before implementation. Not verified MCP entries are an explicit evidence gap, not a claim of absence.

The directory is comprehensive across common project needs, but it is not an exhaustive inventory of every repository, discipline, country or commercial product. Recommendations and selection weights are editorial analysis; service capabilities are supported by the linked documentation.

## A source ledger to keep with every project

Maintain a small record for each source actually used: project question; artifact title; original producer; landing URL; DOI or other persistent ID; exact version or commit; publication and retrieval dates; API query or download method; account or entitlement needed; license and relevant terms; file checksum; transformations; quality limitations; and the decision or claim it supports.

For paper-driven work, add peer-review status, study population, methods and the passage supporting each key claim. For data, add schema, collection period, units, missingness and the split strategy. For code, add runtime, dependencies, test result and pinned commit. For models, add model revision, license, inference settings and evaluation conditions.

The minimum useful deliverable from project research is a short evidence map, a chosen dataset with its documentation, one reproducible baseline, a realistic evaluation plan and a linked bibliography. A long bookmark list becomes valuable only when these pieces connect to a concrete project decision.

## Maintaining the resource map

Before integrating a service, reopen the official documentation and confirm the exact endpoint, version, authentication, access scope and permitted use. Recheck after an API migration, ownership change, relevant release or failed request. Prefer persistent identifiers and versioned artifacts so a changed website does not erase the evidence behind a project.

Add specialist sources when the current collection cannot answer a specific question. Useful expansion routes include re3data for research repositories, national open-data portals for local statistics, disciplinary societies for papers and standards, funder and regulator websites for original records, and the Official MCP Registry or Postman for integration discovery. Verify each newly discovered provider directly.
