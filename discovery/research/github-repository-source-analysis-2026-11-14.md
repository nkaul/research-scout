# GitHub repository discovery — source analysis

Research snapshot: November 14, 2026. This is an implementation reference for a separate **Repos** resource tab. Documentation was checked against official GitHub sources; no user query, repository search, credential or model request was sent to a provider during this research.

## Recommended first slice

Use the saved, valid AI-refined research intent to derive a bounded, problem-specific GitHub query. Search public repository metadata and README scope, return metadata candidates promptly, then acquire a small, explicit README cohort and rerank locally using source passages. Show the actual GitHub query, evidence basis, missing/limited states and acquisition times. Opening a saved tab should only read saved state; explicit discovery or refresh starts provider work. Reuse the existing model plan without adding a hosted-model call or changing the model allowance.

This is vectorless lexical retrieval, not an embedding search or a full-code assessment. Repository popularity is supporting metadata, not evidence that an implementation solves the research problem. Keep GitHub behind its own provider service and provider-bound specialist through application MCP. Official remote GitHub MCP remains a possible later transport, not a prerequisite for public REST discovery.

## Verified GitHub contract

**Search.** `GET https://api.github.com/search/repositories` supports bounded `per_page`/`page`, GitHub best-match ordering and an `incomplete_results` flag. Search only exposes the first 1,000 results; this is discovery coverage, not an exhaustive inventory. Keep query text below its documented size/operator limits and report partial responses. [Repository search REST API](https://docs.github.com/en/rest/search/search).

Without `in:`, repository search covers name, description and topics. Add explicit `in:name,description,topics,readme` for README discovery. Quote meaningful phrases, keep problem/domain anchors and apply application-owned public/fork/archive qualifiers. Do not translate the Papers publication window into a repository creation/activity restriction. README scope does not search arbitrary code files. [Repository search syntax](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories).

**README.** `GET /repos/{owner}/{repo}/readme` can read public resources without authentication. Request `Accept: application/vnd.github+json` explicitly; preserve returned `path`, `sha`, `html_url`, `git_url`, `encoding` and `size`. Validate base64 and decoded bytes before parsing. A stricter application byte cap is a product limit, not GitHub's global limit. Do not render provider HTML, follow embedded links, clone repositories or treat temporary `download_url` values as identity. Optional `ref` selects a branch, tag or commit; otherwise the default branch is mutable. [Repository contents and README API](https://docs.github.com/en/rest/repos/contents?apiVersion=2026-03-10).

The README response's `sha` identifies a **Git blob**, not a commit. Preserve it as `readme_blob_sha`; never manufacture a `/blob/{readme_sha}/README.md` browser permalink. Either retain the supplied current file link with acquisition time and blob identity, or explicitly resolve a commit and fetch at that ref before claiming a revision-pinned browser link. [Git blobs API](https://docs.github.com/en/rest/git/blobs).

**Access and quotas.** Public metadata can work without new credentials. Typical REST primary limits are 60 requests/hour per anonymous IP and 5,000/hour for personal authentication; search has a separate limit of 10/minute unauthenticated and 30/minute authenticated. Shared-IP limits and secondary throttling still apply. Expose observed quota headers, honor reset/`Retry-After`, and stop remaining README dispatches when rate-limited. Never describe anonymous access as unlimited. [Primary rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [search limits](https://docs.github.com/en/rest/search/search).

Use serialized or tightly bounded reads and explicit retry ceilings. Conditional requests can reuse ETags; an unchanged `304` avoids primary quota only when correctly authenticated, so do not promise free anonymous refreshes. A `404` can conceal inaccessible resources: label it unavailable at this public endpoint, rather than definitively deleted or absent. [REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api).

Pin and test the API version. `2026-03-10` is supported; the reference's `2022-11-28` remains supported until March 10, 2028 and should not be described as retired. [API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions).

## Retrieval and UI rules

1. Admit only a valid saved model plan with informative problem/domain anchors; do not silently fall back to a raw question, a generic topic or one isolated word. Record the exact derived provider query and query-policy version.
2. Keep stable identity as provider plus numeric repository ID; names and ownership can change. Require public visibility before retaining README evidence. Keep license identifiers unknown when missing/`NOASSERTION`; public visibility does not grant a reuse license.
3. Rank metadata first, then selected README passages against the problem intent. Keep verbatim supporting text, section and evidence IDs. Preserve negations and relationships; keyword presence alone can match a repository that explicitly does not support the task. Query-dependent selection should consider relevant usage/architecture/benchmark sections rather than blindly taking the first purpose paragraphs.
4. Describe scores as local lexical candidate ordering, not probability, model endorsement or verified functional suitability. Show metadata-only candidates separately from README-supported candidates. Missing README is unknown evidence, not demonstrated irrelevance. A no-match outcome is legitimate.
5. Store metadata fingerprint, README blob/content hashes, parser/ranker versions, query fingerprint, observed time and per-read outcome. Cache compatibility must include all relevant inputs; historical replay must not start GitHub or model work. Do not label a stored observation as a fresh fetch.
6. Keep `created_at`, `updated_at`, `pushed_at` and `fetched_at` distinct. Stars/forks are popularity; README revision is not a release version. Display exact source links and unknown versions honestly. Preserve partial candidates if one README fails, and keep Papers/Videos/Data state and notes intact.

## Bounded acceptance review

Verify exact public scope even with a token; problem-specific query preservation; repository-ID dedupe; README byte/encoding bounds; 404 versus 403/429 states; blob-versus-commit link correctness; metadata-only/README-supported labels; keyword-only false positives and negative statements; stale-search response guards; saved-tab reads without automatic discovery; repeat/replay with no hidden model work; and visible per-search/read budgets. Fixture checks establish contract behavior, not live ranking quality.

## Integration review outcome

The implementation review adopted one public search, at most five anonymous README reads and at most five fresh anonymous public identity checks: **eleven upstream requests maximum**. The identity check follows README acquisition and verifies the candidate's numeric ID/name; a failed check discards README evidence while preserving search metadata. This closes ordinary namespace-reuse races without claiming an atomic multi-request snapshot. Core independently validates source/version/line bounds and recomputes applicability from the saved plan. Conditional-cache identity remains separate from current public identity verification. See the [adopted architecture](../../system-design/github-repositories-2026-11-14.md).

Read-only review covered `repo_evidence.py`, `repo_contracts.py`, `providers/repo_service.py`, `repos.py`, `agents/repos.py` and the Repos frontend. Findings about authenticated README exposure, weak one-token promotion, discarded query constraints, truncation, mutable journal events and mismatched timeouts were addressed before the backend freeze. Execution reported 52 focused synthetic tests passing; full-suite/browser/live validation remains the parent task's responsibility. Lexical/excerpt limits, non-atomic source acquisition and unverified functional suitability remain explicit limitations.
