# MCP integration research and proposed boundary

> **Historical source material — copied 25 October 2026.** This document originated in the GitHub Manager Research Scout work of 23 October 2026. Implementation statements, paths, commands, localhost addresses, test counts and budgets describe that original prototype or proposal, not an implementation in this repository. No code, credentials, data stores or spending authorization are transferred. See the [standalone project scope](../README.md) before using this material.


Date: 2026-10-23. Status: design proposal; no MCP connection, OAuth grant, credential probe, installation, application edit, or paid request was performed. Repository observations below describe source code, not a verified running deployment. External claims were checked against primary sources on this date.

## Decision

**Proposed:** use two separately authenticated MCP connections inside the application's backend agent runtime:

1. Reuse GitHub's official MCP server for a very small set of GitHub reads. The hosted server is the preferred candidate, conditional on an OAuth compatibility spike. A pinned local stdio server with its own disclosed, account-matched OAuth grant is the fallback candidate.
2. Add a GitHub Manager (GHM) MCP server for owner-scoped local workspace reads, proposal persistence, and narrowly authorized application-local changes. Initially mount its ASGI application in the existing FastAPI process and use loopback Streamable HTTP. It delegates to application services/domain functions; it does not manipulate SQLite directly.

The existing OAuth App sign-in and REST/GraphQL inventory connector remain. A GitHub App, PAT, external IDE connector, and GHM MCP capability token are different credentials and are not interchangeable. MCP standardizes tool calls; it does not supply the application's authorization, content policy, approvals, or repository-eligibility semantics.

## Current external facts and their limits

### GitHub server and authorization

GitHub hosts its remote endpoint at `https://api.githubcopilot.com/mcp/`. The open repository supplies the tooling library; the hosted service also has its own infrastructure and some additional tools. Its existence does not prove this application's account, OAuth client or organization can use it. [Official remote server documentation](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md).

GitHub's host-author guide documents pre-registered OAuth Apps and GitHub Apps, bearer tokens, and authorization-server discovery from `WWW-Authenticate`. It explicitly says remote Dynamic Client Registration is unsupported. It also describes supplying an existing valid token, but that is not sufficient evidence that this app's currently issued OAuth App token will pass the deployed remote server's integration checks. Do not hard-code the application's existing OAuth endpoint assumptions into a generic remote-MCP OAuth flow. [Official host integration guide](https://github.com/github/github-mcp-server/blob/main/docs/host-integration.md).

The local stdio server now supports its own browser OAuth login. Official builds include a registered application for GitHub.com; the resulting token remains in memory. Bring-your-own OAuth App/GitHub App and callback configuration are documented. A static `GITHUB_PERSONAL_ACCESS_TOKEN` input takes precedence over OAuth login. That documented static-token name does not establish support for injecting the existing app's OAuth token into it. Local server OAuth is a separate grant and session, with separately requested scopes. [Versioned local OAuth documentation](https://github.com/github/github-mcp-server/blob/v2.0.3/docs/oauth-login.md).

The local server also documents unattended GitHub App installation authentication. This is an alternative requiring different permissions/installation and is outside the initial proposal. No PAT or GitHub App migration is implied. [GitHub App authentication documentation](https://github.com/github/github-mcp-server/blob/main/docs/github-app-auth.md).

**Proposed remote credential broker:** keep the current app OAuth grant in `SessionStore`; create a separate per-user connection record in memory for any approved MCP grant. Resolve a connection using authenticated owner ID, GitHub host, credential kind, scope/permission set and grant version. A narrow, server-side broker selects a credential immediately before each outbound call. It never returns credentials through a model-visible tool. Test reuse of the existing OAuth grant only after checking documented support and resource constraints; otherwise obtain an explicit separate grant using a registered client. Compare `get_me`'s durable numeric ID with the signed-in app identity, reject mismatches, and never attach an operator's token to another user's run.

**Proposed local fallback:** launch one pinned stdio child per authenticated grant/run boundary, with a sanitized environment and no inherited unrelated provider secrets. Prefer a native verified binary; Docker is optional, not a new requirement. Use its separate OAuth flow only after showing the actual scopes and account to the user. Limit callback binding to loopback. If compatibility requires injecting any token, prove the input supports that exact credential type first; do not use token substitution as an undocumented workaround. Tear down the child on logout, expiry, cancellation and idle timeout. Environment-based tokens are accessible to the child process and are never a shared global environment across users.

### Protocol and dependency baseline

The current MCP `latest` specification resolves to **2026-07-28**. Its Streamable HTTP revision removes protocol-level sessions and the GET notification stream; older deployments may still negotiate a handshake/session-based revision. Application login sessions, agent conversation state, jobs and approvals are separate concepts that must persist independently of either transport era. Origin validation and loopback binding remain transport requirements. [Current transport specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).

The official Python SDK's stable v2 line uses `MCPServer` and a first-class `Client`; v1 examples using `mcp.server.fastmcp.FastMCP` are not the current v2 API. The SDK supplies an ASGI app and documents host-owned lifespan management when it is mounted inside FastAPI. The parent must compose that lifecycle with the current background `Service.loop()` and session cleanup. Do not merely mount the route and assume the child lifespan starts. [SDK v2 changes](https://py.sdk.modelcontextprotocol.io/whats-new/), [ASGI mounting documentation](https://py.sdk.modelcontextprotocol.io/run/asgi/).

The separate `langchain-mcp-adapters` repository is no longer actively maintained. Current official LangChain docs recommend `langchain.mcp.MCPAdapter`, available through `langchain[mcp]>=1.4.0` and currently beta. It adapts discovered MCP tools. This LangChain adapter is built on the separate FastMCP package; that package is distinct from the official SDK's former `FastMCP` class. [Adapter repository status](https://github.com/langchain-ai/langchain-mcp-adapters), [current LangChain MCP documentation](https://docs.langchain.com/oss/python/langchain/mcp).

**Proposed concrete spike candidates:** `mcp==2.3.0` for the GHM MCP server; `langchain[mcp]==1.4.7` with the companion proposal's `langgraph==1.2.16` runtime; GitHub local server **v2.0.3** if a local fallback is needed. These are a candidate compatibility baseline, not an installed or tested set. Pin the resolved FastMCP, MCP types and transitive packages after an isolated resolution/contract spike, and preserve the application's existing provider/version constraints. The remote server cannot be version-pinned by the app: record observed capabilities/schema fingerprints and test them. [Python SDK release](https://pypi.org/project/mcp/2.3.0/), [LangChain release](https://pypi.org/project/langchain/1.4.7/), [GitHub server release](https://github.com/github/github-mcp-server/releases/tag/v2.0.3).

Use one adapter/client per server, rather than an aggregate that forces both into one protocol era. Current LangChain docs explain independent clients/`ClientGroup` for different protocol eras and credentials; discovered tools retain their client, and invocations reconnect as needed unless a context is intentionally held. **Proposed policy:** principal-scoped clients/caches; explicit shutdown and bounded idle lifetime; no tools cached with one user's credential and reused by another. [LangChain connection lifecycle and protocol eras](https://docs.langchain.com/oss/python/langchain/mcp/connections).

## GHM server shape and authorization

| Proposed choice | Reason, alternative and revisit condition |
|---|---|
| Mounted Python SDK ASGI server, loopback Streamable HTTP | Reuses the current process's session authority and services with a real MCP boundary. Middleware/SDK verification authenticates every call; do not rely on REST dependencies. Maintain a composite app lifespan and explicit MCP route prefix. Separate process becomes useful when dependency conflicts, resource isolation or independent scaling justify it. |
| No browser-to-MCP calls initially | Browser uses the existing authenticated REST API and CSRF contract; the backend is the MCP host. Avoid exposing bearer credentials to browser storage or prompts. An external MCP client is a later integration with separate consent, authentication and discovery work. |
| Separate audience-bound app capabilities | An internal, pre-registered app client receives a short-lived opaque capability from server-side session authority; store only its digest plus owner, audience, allowed tool scopes, run, expiry and auth-version binding. This is a first-party private transport mechanism, not a claim of complete generic OAuth client interoperability. The GHM endpoint accepts neither GitHub API tokens nor bare browser cookies as MCP bearer credentials. |
| No generic HTTP/filesystem/shell/SQL tool | The model cannot choose an upstream URL, credential, executable, process environment, database query or workspace owner. A separate stdio GHM shim is a later optional adapter and calls the same authorized services; it cannot open the local database as a bypass. |

For a publicly addressable or third-party-client GHM endpoint, add a real OAuth 2.1 authorization server integration and protected-resource metadata/discovery before exposing it. Use pre-registration first, exact redirect allowlists, PKCE/state, consent per client, scopes and validated token audience/issuer/expiry; do not claim the existing GitHub OAuth App is already a GHM authorization server. MCP requires tokens intended for the protected server; accepting an arbitrary upstream GitHub bearer and forwarding it is the forbidden token-passthrough pattern. [MCP authorization requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

The official Python SDK offers a token-verifier interface, but implementing correct token validation, owner authorization and operation-specific scopes remains application work. Enable resource/audience checks explicitly; do not assume a library's current defaults validate them. [SDK authorization documentation](https://py.sdk.modelcontextprotocol.io/run/authorization/).

**Proposed authorization layers:** browser mutating request passes existing Origin/CSRF/session checks → backend binds run to owner/collection → broker creates an audience-bound GHM capability → MCP middleware verifies it per request → each tool resolves workspace from authenticated context and checks its scope → domain/service rechecks access, version, fences and invariants inside the mutation. Reject any supplied owner/workspace override. Production HTTPS/secure cookies and encrypted provider credential storage remain later deployment work, not changes delivered by this proposal.

Server-to-server bearer calls do not carry browser CSRF cookies; they use distinct authentication, exact Host/Origin validation when Origin is supplied, and no permissive browser CORS. A CSRF-protected browser approval creates a server-owned approval record. Neither omitting Origin on a backend call nor knowing an MCP transport handle constitutes user authorization.

## Tools, policy and review contracts

GitHub server configuration supports exact tool lists, a read-only filter, and exclusions; the read-only filter takes precedence. These are useful defense layers, but do not narrow a broad OAuth grant at GitHub. Lockdown filtering is explicitly best-effort, so it is not a privacy/security boundary. [GitHub server configuration](https://github.com/github/github-mcp-server/blob/main/docs/server-configuration.md).

**Proposed phase/profile allowlists:** A2 Investigator starts with `get_me` and `get_file_contents` only, with server-enforced read-only mode. Its host wrapper constrains reads to the selected repository's exact approved README and at most two named supporting text-file references, bound to immutable revisions and byte ceilings. These references are established in the task preview; a new path needs scope review rather than arbitrary browsing. A3-S Scout may separately add a reviewed public repository-search tool, bounded brief-derived queries, candidate counts and newly public-verified candidate references. Search is not available merely because the server exposes it. Add individual PR/issue reads only for a later approved profile and reviewed schema. Do not enable an entire default toolset, unbounded search, recursive resources, workflow dispatch, issue/comment creation, stars, labels, branch operations or repository writes. The existing deterministic inventory sync retains owner/team/contributor/favorites semantics; GitHub MCP search is not a replacement.

**Proposed host enforcement, applied before every tool call and after every result, including third-party reads:**

- Bind namespace, exact tool and method, server identity and schema fingerprint to a static manifest. Discard unapproved tools returned by discovery; stop affected calls on schema drift. Tool descriptions, annotations and returned text cannot grant permission.
- Resolve stable repository identity/access from trusted state. Restrict host, repository, README path/revision and collection to the approved run scope. Deny generic URLs, traversal, arbitrary GraphQL, follow-up resource links and automatic downloads. A GitHub tool returning a resource link is not permission to fetch it.
- Keep raw GitHub content on the trusted side of a content gateway. Revalidate access and the model data-sharing policy, limit bytes, normalize the MCP response, and select bounded evidence using the existing local extraction policy before forming any model `ToolMessage`. No adapter may send a raw response directly into model context.
- Treat README/issue/comment/tool-result text as untrusted data. Preserve source identity, hash and excerpt positions; redact secrets and control/active markup; do not follow instructions embedded in content. Public material can also contain credentials or prompt injection.
- Private-derived metadata, keywords and purpose sentences remain private. An unauthorized private result is withheld from the LLM and its checkpoint/transcript/trace/export, even if GitHub returned it successfully. The first live slice is one explicitly selected **public** repository; private-content behavior is proven with synthetic denial fixtures first.
- Apply finite tool-call, byte, deadline, retry and provider budgets outside the model. Log sanitized result/error codes, IDs, policy decision, bytes and attempt count. Do not log headers, environment, cookies, credential values or raw private tool results.

**Proposed GHM tool catalog:** names below are application contracts, not upstream MCP tool names or already implemented endpoints. All inputs/outputs use strict Pydantic models with bounded arrays/strings, unknown-field rejection and explicit output schemas. Owner identity and credentials come from authenticated context, never model parameters.

| Proposed tool | Input → bounded result | Authority/effect |
|---|---|---|
| `ghm_get_workspace_context` | Collection enum → capabilities, active taxonomy revision/fences, privacy/budget policy summary, sync coverage/freshness | Read; no raw aggregate/SQLite dump. |
| `ghm_list_repositories` | View/filter, bounded page size, opaque cursor → stable repo IDs and permitted metadata, next cursor, partial-coverage warnings | Read; cursor bound to principal, collection, filter and snapshot. |
| `ghm_get_repository_context` | One stable repo ID → approved current evidence references, allowed compact profile, existing associations and protected user decisions | Read; current access/privacy checked on every call. No arbitrary path. |
| `ghm_search_registry` | Bounded query/kind/filter/cursor → active canonical IDs, definitions, aliases and revision | Read; limited to caller workspace; source scores are candidate ranking, not assignment decisions. |
| `ghm_save_proposal` | Repo IDs, existing concept IDs, rationale/evidence refs, confidence, expected revision/fences, idempotency key → persisted draft ID and validation outcomes | Application-local draft write only; preserves rejections/manual edges and records agent provenance. Cannot publish a concept, label a GitHub repo or accept itself. |
| `ghm_preview_change_plan` | Valid draft ID and bounded selected operations → immutable plan ID/hash, exact diff/counts, preconditions, expiry and approval requirements | Application-local preview write; no accepted taxonomy/mapping effect. |
| `ghm_get_plan_status` | Plan ID → pending/approved/applied/rejected/expired/stale, bounded receipt | Read with owner checks; no approval capability returned. |
| `ghm_apply_approved_plan` | Plan ID plus idempotency key → atomic result or existing receipt | **Deterministic executor only**, omitted from model tool catalog. It additionally needs a one-use approval capability in server context with an apply scope. |

`ghm_save_proposal` is deliberately a write despite being non-destructive. Its scope is separate from read-only workspace and GitHub-read scopes. In A2, `ghm_apply_approved_plan` accepts exactly the approved operation kinds `SAVE_REVIEWED_BRIEF` (store a human-reviewed generated brief and its evidence/source references) or `APPLY_EXISTING_ID_MAPPING` (add the exact reviewed existing canonical mapping through current domain rules). Each operation has its own immutable plan content and idempotent receipt; saving a brief is not a classification or canonical label decision. A3-S may add `SAVE_REVIEWED_SHORTLIST` for the separate research collection after its contract is reviewed. Domain/project CRUD, merge/archive, rule changes, budget/allowance changes, reset execution, provider configuration, GitHub writes and arbitrary job start remain unavailable through agent tools. Existing UI workflows remain usable.

**Proposed approval record:** owner, collection, run/draft/plan ID, canonical plan hash, exact operations/repo/concept set, evidence/source version, generation/epoch/revision/policy preconditions, auth-version binding, expiry and consumed status. The existing UI displays the concrete diff and records approve/reject via a CSRF-protected action. The model cannot produce or change this record. A deterministic graph node requests execution with the hidden capability; the server revalidates ownership, current access, expiry, hash, fences and domain rules transactionally. Repeating the same apply returns the persisted receipt; a changed cohort, policy, user correction or reset requires a new preview and approval. A disconnect is not a rejection or permission to execute again.

**Proposed result envelope:** structured `ok`, typed `data`, source/evidence refs, `next_cursor`, `truncated`, coverage/freshness warnings, operation receipt and a sanitized typed error when applicable. Examples include `REAUTH_REQUIRED`, `ACCESS_DENIED`, `PRIVACY_BLOCKED`, `STALE_PLAN`, `RATE_LIMITED`, `UPSTREAM_UNAVAILABLE`, `POLICY_DENIED` and `OUTCOME_UNKNOWN`. Authentication failures remain HTTP authorization errors; domain/tool failures remain typed MCP tool results. The graph decides recovery from codes, never by obeying prose returned by a tool.

## Failure and isolation behavior

| Case | Proposed behavior and evidence required |
|---|---|
| Missing/expired app session, provider 401, logout | Fail closed before the next tool/commit, cancel outbound work where possible, revoke GHM capabilities and local child, redact credentials. Preserve draft/history. Require reauthentication and explicit resumption; never reuse another session's newer grant automatically. |
| New login is a different GitHub account | Numeric ID mismatch blocks the MCP connection and old approval. Rebuild owner-scoped clients/catalog/cache only after explicit account connection. |
| SSO/org policy denial or private 404 | Surface unavailable/partial coverage without leaking hidden names. Do not retry with PAT, operator grant, alternate account or broader scopes. Existing local cached content still follows visibility/access policy. |
| Rate limit, 403/429, timeout or transient upstream failure | Classify permission denial separately from rate limiting; honor available retry/reset information and bounded jitter/backoff. Cap total attempts/deadline per run; avoid multiplying adapter + HTTP + graph retries. Use current cached evidence with a freshness warning when permitted, or stop with retry guidance. Missing remote rate metadata is unknown, not an invented quota/reset time. |
| Lost MCP response after local apply | Query plan/receipt status using the same idempotency identity before retrying. Never repeat a state-changing or paid action based solely on a transport timeout. |
| Backend/stdio child restart | In-memory credentials disappear; reauthenticate/reconnect. Recover persisted proposal/approval/receipt state through current store recovery semantics. Ambiguous paid outcomes retain conservative holds; do not replay inference automatically. |
| Reset/manual edit/access revocation during run | Check fences and access again before persistence/application. Retain a valid historical analysis receipt if allowed, but discard stale association effects. Preserve user mappings/rejections. |
| Parallel users, tasks or tool calls | Principal/run-scoped auth context and caches; bounded concurrency; no process-global mutable Authorization header. Transactional plan consumption and one active applicable workspace operation. Concurrent denials must prove no cross-owner rows/content are returned. |
| Remote tool-list/schema change or new server | Freeze a per-run allowlist/schema fingerprint; invalidate/review an affected cached catalog. Never auto-enable a discovered capability. Remote outage disables that capability while existing manual workflows continue. |
| Malicious tool output/OAuth metadata | Output is data, never routing/credential instructions. Validate endpoints and redirects against a reviewed server/authorization-host allowlist, block private-network discovery/SSRF, and require a configured server identity. No model-supplied MCP URL or stdio command. |

## Dependency gates and acceptance evidence

These are future implementation pretests after approval of the design. This research did not run them.

1. **Offline dependency/protocol gate.** Resolve the candidate versions in isolation; record a lock and license/version inventory without disturbing the current app. Prove a GHM server using the official SDK accepts the chosen LangChain client, structured schemas, errors, cancellation and mount lifespan. Test modern discovery and a legacy GitHub-like handshake fixture independently; do not mandate a protocol version unsupported by the real GitHub endpoint. Reject unknown tools/fields. Evidence: sanitized negotiated capabilities, protocol era, schema hashes, fixture outcomes and exact dependency lock.
2. **Offline authorization/content gate.** Two synthetic owners; missing/wrong-audience/expired/wrong-run capabilities; CSRF denial on browser approval; workspace override attempts; public/private/mixed/sensitive text; raw third-party result containing prompt injection and resource links. Prove no blocked text reaches prompts, graph checkpoints, traces or exports. Test a stale plan, repeat apply, concurrent approval, logout, reset and result lost after commit. No credentials or raw private examples in reports.
3. **GitHub remote auth gate.** Check actual `WWW-Authenticate`/protected-resource metadata; establish registered OAuth client support with the current app's OAuth App configuration and policies. Obtain user approval for any new grant. Test the exact credential type, identity match, effective scopes, allowlisted read-only tool catalog and one permitted public README. Do not claim one public success proves organization/private access. If remote cannot support this OAuth App integration, record the concrete denial and evaluate the disclosed local OAuth fallback; do not switch to a PAT or GitHub App.
4. **Local fallback gate, only if needed.** Verify v2.0.3 binary/checksum and OAuth/callback behavior for the chosen host. Prove two concurrent principals cannot share a child/grant, account mismatch is blocked, scope request is reviewable, no token persists to disk, environment is sanitized, and logout kills/revokes the connection. Test existing-token input only if specifically documented for the actual token type; otherwise use its separate OAuth grant.
5. **First useful live slice.** One explicit public repository → current app context → a necessary GitHub MCP source read → host-filtered compact evidence → agent brief or existing-ID draft → concrete UI result/diff → human approval → deterministic GHM MCP apply of `SAVE_REVIEWED_BRIEF` or `APPLY_EXISTING_ID_MAPPING` → persisted receipt and visible local result. The acceptance case must exercise both real MCP connections and an observation-dependent action; ordinary well-evidenced tasks may reuse sources and avoid an unnecessary upstream read. Use the existing provider admission/ledger and an explicitly approved finite live budget. No private content, GitHub modification, taxonomy publication or reset is needed to prove this slice.
6. **Before broader access/deployment.** Validate organization/SSO/private fixtures under an approved sharing policy, encrypted durable credential/session architecture, revocation, multi-process ownership, storage adapter and real remote rate-limit handling. External GHM clients additionally require the OAuth authorization-server/resource discovery/consent gate described above. A new third-party connector is not enabled merely because it is installed in a developer tool.

The first two gates can be completed without a live GitHub credential or model request. Remote OAuth incompatibility blocks that connection, not all useful agent planning/proposal work. The system must label cached-only, fixture-only and live-MCP evidence distinctly; a cached fallback cannot be presented as a completed MCP integration demonstration.
